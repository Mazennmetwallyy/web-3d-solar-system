Solar System Explorer

What I made, why I made it that way, and what went wrong.

What I built

Project Overview

This is a solar system web app with two primary pages. The home page has all eight planets orbiting the Sun in three dimensions. Once you click on any of these planets, you will be taken to an Explore page which allows you to spin the planet around in any direction, change how the surface of that planet looks, and read facts about it loaded from a PHP backend.

A solar system was the theme I chose since planets are simply spheres — therefore I did not need to contend with complicated geometry and could spend most of my time working with shaders and lighting.

Technologies used:

  • THREE.js — 3-dimensional rendering
  • PHP + SQLite — backend database containing planet data
  • Bootstrap 5 — layout & responsive navigation
  • Web Audio API — procedural background sound
  • Canvas 2D — all planetary textures are generated at runtime
3D Models

Blender – Solar System X3D Models

I made all 3D models of the Solar System using Blender version 4. Using Blender's Python scripting API (bpy), I wrote a Python script that programmatically generated the entire solar system scene within Blender, which is why it can be exported as X3D files (ISO Web3D standard) and used directly in a browser or an X3D viewer.

What the script does:

  • Geometry — I created all objects by adding UV Spheres with Subdivision Surface modifiers to get the smooth shapes I wanted. I also had to make the ring systems around Saturn and Uranus manually using Boolean Difference operations because Blender didn't have a straightforward way to do this.
  • Materials — I applied a Principled BSDF to each object with physically based metallic, roughness, and emission values. I set the Sun to emit light at strength 5 in order to make itself glow brightly enough to illuminate the rest of the scene.
  • Procedural Textures — I created procedural textures for Mercury, Earth, and Mars using Noise Texture nodes. For Jupiter and Saturn I added Wave Texture nodes to give them their striped pattern.
  • Lighting — I have a Point Light at the origin of the Sun with energy 5000, a colour temperature of about 4000K (warm yellowish), and a very low ambient world shader so you can still see planets that are behind other planets.
  • Cameras — I have several named cameras: an overhead camera looking down at the whole system from above, another one looking down but slightly tilted for a better view of the inner planets, a camera focused in on just the Sun, and cameras focused in on Earth, Saturn, and Jupiter.

Design decisions

Why I made certain choices

A dark background was an obvious choice — since the entire 3D scene will fill the screen, anything lighter than that would compete against it. The gold colour for accents seemed fitting for the space theme, and it provides enough contrast for the user to read. For layout and navigation Bootstrap provided what I needed, however everything else is custom CSS based on variables so colours were always consistent.

The side panels use a backdrop blur, so although the panels are visible, you can still see the 3D scene through them. On a mobile device they slide out of view and back in by clicking a toggle button. I was able to partially correct a blur flicker bug in Safari iOS when rotating a planet with one of the side panels open — unfortunately this appears to be a known browser issue.

I tried to keep things organised for the backend as well — Planet.php manages all of the database calls, api.php manages the routing, and the JavaScript simply makes API calls and updates the 3D scene. There is also a static fallback which allows the application to function even if a PHP server isn't running.

Accessibility

What I considered

The biggest problem with making a WebGL canvas fully accessible is that ultimately, it's simply an image rendered onto a canvas. Therefore, my focus was entirely on what I can directly influence. Every single one of the three pages includes a skip link that will appear when you click on it using your Tab key. I employed actual semantic elements (header tags and footer tag) instead of nesting divs. In addition, I set up the info panel as aria-live which enables screen readers to announce changes made to this area. Furthermore, I also applied aria-pressed to every toggle button, enabling its current status to be announced.

Additionally, the Explore page works completely with the use of the keyboard. Users may cycle through all of the available planets by using the left and right arrow keys — no need for a mouse. I also implemented prefers-reduced-motion support so the orbits stop moving upon enabling reduced motion in the user's operating system preferences. Lastly, I reviewed all text colour combinations against WCAG AA contrast ratio requirements and had to increase the contrast ratio of the muted colour due to it having failed to meet contrast requirement standards at smaller font sizes.

What I struggled with

The parts that took longer than expected

These are the issues with my project that were difficult or required additional time to resolve, and how I resolved them.

GLSL Shaders

This was my first experience writing GLSL shaders, so this task took longer than expected. I created three shaders: one for the Sun's surface, another for the atmospheric glow around the planets, and a final one for the background nebula.

The atmosphere shader was by far the most difficult part. Initially the glow was always showing up on the opposite side of the planet from where it should have been. After debugging I realised I was comparing the surface normal against the camera direction but the two vectors were in different spaces — the surface normal was in eye space due to THREE.js's normalMatrix, whereas the camera direction was in world space, so the comparison made no sense. I found the solution in an older Stack Overflow question. As soon as I switched both vectors to the same space, it worked perfectly.

Alpha Compounding

To create a Martian surface texture I drew many soft translucent circular blobs (about 37 total), each with an opacity of 0.5. Instead of a textured rocky surface, all the blobs combined into one large black circle. Alpha compounding occurs when multiple transparent layers are drawn on top of one another — unlike regular addition, transparent layers combine according to the formula 1 − (1−α)^N, so 37 circles at 0.5 opacity ends up nearly fully opaque. To fix this I calculated the per-circle alpha value needed to achieve the level of darkening I actually wanted, which turned out to be approximately 0.012. There isn't much documentation on this — you mostly learn through trial and error.

Bloom Post-Processing / Exposure & Brightness Values

I implemented bloom post-processing to help the Sun stand out by making it brighter and glowing. What I didn't realise at the time was that changing either the bloom threshold or the exposure would cause the nebula background to bleed purple throughout the entire scene, because bloom was reading off the nebula's output. In other words, adjusting any one of these three values affected all three. I had to tune all of them simultaneously rather than independently.

Orbiting Moons

Initially I attempted to calculate the moon's world position relative to its planet each frame using basic trigonometric equations. While this worked at first, it failed whenever the planet moved since I was working in a coordinate space that changed along with it.

The correct approach is to attach an empty Object3D to the planet's orbital pivot and parent the moon to that empty object. When you rotate the empty object it inherits all of the planet's motion automatically, without requiring manual position updates. While obvious now, I spent considerable time attempting to implement this incorrectly before figuring out the right way.

Loading Screen Hanging with No Server

When the PHP server wasn't running, fetch() would just hang indefinitely with no error. The page looked completely frozen and the only way out was a hard reload. I fixed this using AbortController to cancel the request after 2.5 seconds and fall back to hardcoded JSON data. The same issue came up with CDN textures, so I ended up generating everything procedurally with Canvas 2D — which also means the app has no external dependencies that could break.
