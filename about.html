Solar System Explorer

How I built it, the decisions I made, and what I struggled with.

What I built

Project Overview

I built a solar system web app with two main pages. The home page shows all eight planets orbiting the Sun and you can click any of them to go through to the Explore page, where you can rotate the planet, switch between surface modes, and read facts about it pulled from a PHP backend. I picked a solar system theme because planets are just spheres, which meant I could spend more time on the shaders and lighting rather than struggling with complex geometry.

The main technologies I used were THREE.js for the 3D, PHP and SQLite for the backend, Bootstrap for the layout, and the Web Audio API for the ambient sound. All planet textures are generated at runtime using Canvas 2D — there are no image files in the project at all.

3D Models

Blender – Solar System X3D Models

All 3D models were authored in Blender 4 using its Python scripting API (bpy). A Python script programmatically built the entire solar system scene inside Blender and exported the models as X3D files (ISO Web3D standard) for use in the browser.

  • Geometry – UV Spheres with Subdivision Surface modifiers for smooth silhouettes. Ring geometry for Saturn and Uranus was created using Boolean Difference operations.
  • Materials – Principled BSDF materials with physically accurate metallic, roughness and emission values. The Sun uses Emission Strength 5 to self-illuminate.
  • Procedural Textures – Noise Texture nodes for rocky surfaces (Mercury, Venus, Earth, Mars). Wave Texture nodes for gas-giant banding on Jupiter and Saturn.
  • Lighting – Point Light at the Sun's origin (energy 5000, warm colour temperature) plus a dim ambient world shader.
  • Cameras – Multiple named cameras: top-down overview, angled overview, close-up Sun, and individual planet close-ups for Earth, Saturn and Jupiter.

Design decisions

Why I made certain choices

Dark background was an obvious choice since the 3D scene is the main thing on screen — anything lighter would fight with it. The gold accent colour felt right for a space theme and it stands out well on dark backgrounds. I used Bootstrap for the grid layout and the responsive navigation, but most of the styling is custom CSS using variables so it was easy to keep things consistent.

The side panels use a blur effect so you can still see the 3D scene through them slightly. On mobile they collapse off-screen and come in through a toggle button. This caused a flickering issue on Safari iOS that I only half fixed — it's a known browser bug and I couldn't get around it completely.

For the backend I followed an MVC pattern — Planet.php handles the database queries, api.php routes the requests, and the JavaScript files make fetch calls and update the scene. I also built a static fallback so the site works even without a PHP server running.

Accessibility

What I considered

WebGL content is hard to make fully accessible since it's essentially a bitmap drawn to a canvas. I focused on the things I could actually control. There's a skip link on all three pages that appears when you tab to it. The panels use proper semantic elements like <main> and <aside> rather than just divs. The info panel announces changes to screen readers with aria-live, and all the toggle buttons have aria-pressed states.

The Explore page supports keyboard navigation — left and right arrow keys cycle through all the planets without needing a mouse. I also implemented prefers-reduced-motion so the orbits pause automatically for users who have that turned on in their OS settings. I checked all text colour combinations against WCAG AA contrast ratios and adjusted the muted text colour because it originally failed at small sizes.

What I struggled with

The parts that took longer than expected

This section is about the specific things that didn't work first time and what I had to figure out to fix them.

GLSL shaders

I'd never written raw GLSL before so this took a lot longer than I expected. I wrote three shaders from scratch — the Sun surface, the atmosphere glow around planets, and the nebula background.

The atmosphere one was the most frustrating. The glow was appearing on the wrong side of the planet for ages and I couldn't work out why. It turned out I was transforming the surface normal into the wrong coordinate space — THREE.js's normalMatrix gives you eye space, not world space, so comparing it against the camera direction was giving completely wrong results. I eventually found the explanation on an old Stack Overflow thread. Once I fixed that it worked straight away.

Alpha compounding when drawing textures

For Mars I was drawing lots of overlapping soft shapes to create Valles Marineris and set each one's opacity to about 0.5, thinking they'd add up to a semi-transparent result. Instead I got a solid black stripe. The issue is that transparent layers don't add — they compound using the formula 1 − (1−α)^N, so 37 layers at 0.5 opacity becomes basically fully opaque. I had to calculate what alpha each individual blob needed to achieve the overall darkening I actually wanted, which came out at about 0.012 per blob. This isn't mentioned anywhere obvious, you just run into it.

Bloom and tone mapping breaking each other

I added post-processing bloom so the Sun would glow properly. What I didn't realise was that the bloom threshold, the tone mapping exposure, and the nebula shader brightness are all connected. When I increased the exposure to make the planets look brighter, the nebula background started bleeding purple onto everything because the bloom was picking up its output. I had to tune all three values together rather than independently, which took a while to get right.

Getting moons to orbit correctly

My first attempt at adding moons was to manually calculate their world position every frame using trigonometry. This worked until the parent planet moved, at which point the moon would jump to the wrong place because I was working in the wrong coordinate space.

The proper solution is to nest an empty Object3D inside the planet's orbital pivot at the planet's position, and put the moon inside that. Then you just rotate the empty object and the moon inherits all the planet's movement automatically — no manual position calculations at all. It seems obvious once you know but I spent a while on the wrong approach first.

The loading screen hanging with no server

If the PHP server wasn't running, fetch() would just hang indefinitely with no error. The page looked frozen and the only way out was a hard reload. I fixed this by using AbortController to cancel the request after 2.5 seconds and load a fallback JSON file instead. The same thing happened with texture loading from a CDN — in the end I removed all external texture fetches and generate everything procedurally, which also means the site has no external dependencies.
